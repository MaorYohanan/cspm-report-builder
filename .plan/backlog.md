## Reporting & PDF

### BL-01 · Risk Score Trend Chart (Product Timeline)
**Why:** The product timeline lists published versions but gives no visual sense of whether posture is improving or deteriorating over time.
**Effort:** Medium (was High — PDF constraint removed)
**Design (grilled 2026-09-07):**
- Lives on the **product timeline UI page** — not in the PDF
- Chart type: line chart (SVG)
- X-axis: **version number** (e.g. 1.0, 1.1, 2.0) in chronological order
- Y-axis: Risk Score value
- Data: last **5 published versions** of the product (or fewer if less than 5 exist)
- Exact placement on the timeline page decided by the designer agent
- Data source: `ReportSnapshot.risk_score` for published snapshots — already stored, no new backend fields needed
- Backend: may need a lightweight endpoint or reuse existing version-list endpoint to return risk scores
**Notes:** Distinct from the Regression Chapter (already shipped) which compares two snapshots side-by-side. No overlap with existing code.

### BL-03 · Draft Watermark on Unpublished PDF
**Why:** Reviewers receiving draft PDFs have no visual indicator that the document has not been published and may contain unreviewed content.
**Effort:** Low
**Design (grilled 2026-09-06):**
- Diagonal text stamped across **every page including the cover**
- Text: `"טיוטה"` when PDF language = Hebrew, `"DRAFT"` when PDF language = English (follows the existing PDF lang toggle)
- Style: light grey, ~20% opacity — must not obscure content underneath
- Condition: watermark appears only when `ReportSnapshot.status = "draft"` (never on published PDFs)
- Technique: designer agent decides (CSS `position:fixed` `body::before` with `@media print` is a candidate; must survive Playwright renderer)
**Notes:** No watermark logic exists anywhere in `pdf_service.py`, `report_template.html`, or the JS export path. Fully new. The draft/published distinction is tracked in `ReportSnapshot.status`, so the condition is easy to check before render.

### BL-04 · PDF Bookmarks / Named Destinations

### BL-24 · Exception Carry-Forward Hardening
**Why:** The current carry-forward mechanism matches solely on `(subscription + title)` string pair. This is fragile: if Wiz renames a rule, changes a subscription name, or aggregates several sub-findings under a new title, the exception silently fails to re-apply and the finding reappears as active in the next cycle — with no warning to the consultant. Aggregated findings compound this: a single Wiz "aggregated" entry may represent N underlying findings, so a title-level match may over- or under-match when the aggregation grouping changes between scans.
**Effort:** High
**Notes:** Requires deep design work before any implementation. Open questions that must be resolved first: (1) Should the match key include Wiz rule ID, CVE identifier, or a content hash alongside the title? Needs to account for aggregated findings where there is no single stable ID. (2) Should a failed carry-forward (no match found for a previously excepted finding) surface as a consultant warning rather than silently disappearing? (3) How does the proposed BL-23 Acknowledge/Exclude split interact with this — the two features must be designed together. (4) Does `ExcludeRule` (currently browser-only) need to be applied server-side in the pipeline scan path for consistency? **Do not implement until a design session has been completed and the open questions above are answered.**

### BL-23 · Acknowledge vs Exclude — Dual Dismissal States
**Status:** ✅ DONE — merged to main 2026-11-08. Delivered as `exception.kind` ('acknowledge' vs legacy exclude) on top of `exception.active`, with an Alembic migration. The text below is the original pre-implementation note and is kept for history only; the note "no migration framework — manual ALTER TABLE" is superseded by Alembic (`migrations/`). BL-24 below remains design-first (it must be designed together with the shipped acknowledge/exclude split).
**Why:** The current single exception boolean collapses two meaningfully different decisions — "this finding is a false positive / irrelevant" and "this finding is real but we have investigated and accepted the risk for a period" — making it impossible to distinguish noise suppression from documented risk acceptance in audit trails or report chapters.
**Effort:** High
**Notes:** NET-NEW. The `Finding` model currently has one dismissal field: `exception_active` (boolean, `models.py:85`) with a reason string inside `finding_data`. No `dismiss_type`, `acknowledge`, or `exclude` field exists anywhere in the model, routes, or UI. The `ProductMemoryEntry.source` field (`excepted`/`deleted`) is a pipeline-memory concept, not a per-finding dismissal state. Implementation requires: (1) a new field on `Finding` — either a string `dismissal_type` enum (none/acknowledge/exclude) replacing `exception_active`, or a companion boolean `exclude_active` alongside the existing `exception_active` (rename to `acknowledge_active`); (2) optional `exclude_until` date field for time-limited exclusions; (3) DB migration (no migration framework — manual ALTER TABLE or re-create); (4) updated risk score logic in `compute_risk_score()` (both states exclude from score); (5) two distinct UI action buttons in the finding detail pane (replacing the single "החרג" button); (6) a "show acknowledged only" and "show excluded only" filter in the findings list; (7) PDF template change — acknowledged findings continue as today (exception banner in Section 4); excluded findings optionally appear in a new "Excluded Findings" sub-section distinct from the main finding cards; (8) update `ProductMemoryEntry` pipeline memory source to carry the dismissal type so future scans restore the correct state.

### BL-30 · Unsaved-Data Warning on Version Load / PDF
**Why:** In the product history / timeline view, clicking "LOAD" (load a version for editing) or "PDF" (render that version's PDF) silently replaces the current in-memory findings with the findings stored in the selected snapshot. Any unsaved edits — new findings typed since the last save, field edits, exception toggles — are permanently discarded with no warning.
**Effort:** Low
**Design:**
- Intercept both "LOAD" and "PDF" button clicks in the product timeline / version history panel (in `products.js`).
- Before executing the action, check whether there are unsaved edits: compare `state.findings` (current in-memory) against the last-saved state, or use an existing `isDirty` flag if one exists.
- If unsaved edits are detected: show a `styledConfirm` dialog (Hebrew): **"קיימים שינויים שלא נשמרו. אם תמשיך, הנתונים הנוכחיים יאבדו. להמשיך?"** with "כן, המשך" / "ביטול" actions.
- If the user confirms: proceed with the original LOAD or PDF action.
- If the user cancels: abort — do nothing.
- If no unsaved edits are detected: proceed without showing a dialog.
**Notes:** NET-NEW. No dirty-state guard exists before version switches. The check does not need to be exhaustive — comparing `state.findings.length` and a hash/timestamp of the last save is sufficient; a false-positive (showing the dialog when nothing actually changed) is acceptable and far safer than a silent data loss.
